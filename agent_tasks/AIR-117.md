# Task description

We have already built compile-time expressions. Now the task is to build runtime expressions.


# Syntax features

To reference a field, the syntax `field("myfield")` and its shorthand `` `myfield` `` now work.
A strict requirement: for `"myfield"` the value must be computed at compile time — i.e. the
argument must be `is_const` after all evaluation passes. (Some scripting tricks are allowed, but
after optimizations it must reduce to a constant.) The whole body can also be obtained, serialized
to JSON, via `fields("*")`, or only a subset of fields via `fields("field1,field2")`.

Also `field(field("myfield"))` and likewise `field(\`myfield\`)` collapse into `field` during folding.

Importantly, backticks cannot take arguments — they are simply a specific literal.

Also document in the project conventions, in the expression docs, and in the config docs that for
YAML it is preferable to write `field` instead of `"\`field\`"`.

# Structural features

We follow AIR-123.md — expose a minimal interface, hide the maximum in the implementation.

A new module `expr/optimize` is added.
It introduces a new (optimized) syntax tree and the algorithms that build the optimizations.

The evaluator moves into it (since it is needed for const folding), and the runtime will then
depend on it. The new AST structure etc. live there as well (see below).

The runtime, in turn, gains a new evaluator over the new structure, which we use everywhere.


We also add a type checker, based on the type resolver.
First, it validates type errors; second, it fails on syntax errors.

For now the rules are:
1. you cannot call non-const functions in a compile-time context;
2. you cannot pass a non-const string into `field("field")`;
3. if the source schema exists and the field is not in the spec.

Overall I propose a separate `RuntimeProgram` mechanism so as not to confuse it with an ordinary
program, because their execution mechanics are completely different — a runtime program requires a
schema for type checking, field validation for type checking, and argument passing via a
field-index table.

Of course we check types the same way and do truncate with type validation the same way. And we
require a default the same way. But in compute-mapping the defaults are truncate = false and
default = null, because everything can easily be done via scripts if needed.

# Where scripts run

Scripts appear in two places.

1. When computing fields, a `compute` field appears that explicitly blocks the use of `from` and
`switch`. `default` keeps working correctly and `truncate` keeps working correctly too.

2. We also add the ability to use the shorthand syntax via compute-mapping. The values in
compute-mapping go into the main array after:

```
[flow.users.compute-mapping]
id = "`_id`"
name = "`name`"
static_literal = "static-literal"
```

That is, runtime scripts execute ONLY in the transform.

# Compile-time functions and context

Every function now gains an `is_pure()` method in order to determine which ones may be called at
compile time and which may not. We also extend the `random` function to two arguments and add a
seed. If the seed is constant, then it is const. `now()` is always `is_pure` false. So constness
depends on the argument count.

We also add a flag to the context indicating whether it is compile time. If it is, then calling
`is_pure` functions fails with an error.

An additional point — we now pass the context into the transform (via an Arc) and initialize a
local context with a new time every time a batch is formed. (That is, it is a new context with a
reference to the old one.) In general we make the context an interface and initialize it via a
generic.

# Caching

We add a cache to the context. Since the context is now global rather than local, we cache parsed
expressions for JS path and for regexp in global caches that live in the context under an
`RWLock<ahashmap>`, and we add functions like `get_regexp_cached(&self, &str) -> guard<'a, &regex>`.

Do an explicit investigation of what else can be cached. The cache goes into the context. The
cache implementation is trivial — a hash map with a FIFO queue that resets after 1000 elements.
We make a local cache per flow. The default size is 0. The shared cache implementation goes into
commons as a separate caching crate (made thread-safe right away).

# Optimizations

1. minor optimization.
   In `FuncRef` keep a single index and pass arity to `FunctionRegistry.get_ref`.
   Remove the method `FunctionRegistry::pub fn resolve(&self, name: &str, arg_count: usize) ->
   Result<&'static dyn ExprFunction, FuncError>`.
   Use the method `get_by_ref(FuncRef)` instead.

   Also fail with an error when attempting to re-register a function with the same or overlapping
   arity.
2. optimizations are done in `optimize` on an ADT on the heap, and the final representation is on
   arenas.
3. optimization via arena. We make a custom arena entity (put it in commons). It is a generic from
   which you can get either an `ArenaRef` slot via allocation, or an `ArenaSlice`. Our arenas use
   `u16` indexing and if the index is larger — fail explicitly when forming the arena.
4. what do we store in the arena?
    a. the optimized ADT based on the ADT after optimizations, filling the arena in execution order;
    b. a separate buffer for constants, with references to it living in the first ADT. Why a
    separate arena here? Because constants have a different layout as a value and may be larger;
    b. not quite an arena. A set of registers (we have an essentially register-based interpretation)
    for statements. We replace all variable names with register ids;
    c. a separate buffer for function references.

   (Actually let's discuss — maybe one arena is enough for optimization, just split the const block
    and the non-const block; maybe for our script sizes no `u16` is needed at all, and we do
    optimizations on the arena and then compact; the point of optimizing on the heap was to avoid
    overflowing `u16` during iterations.)

5. which optimizations do we apply on the heap before forming the arena?
   6. const folding. all const expressions are computed immediately.
   7. flattening. for expressions that support it, e.g. sum, concat, etc. — expand nested trees
   immediately.
   8. Dead code elimination. in any branching where we can drop one of the branches — drop it
   immediately.
   9. const inlining. we compute statement values at the start of optimization, and if a statement
   is entirely const we remove it from the registers and just replace it with the constant in the
   tree, then continue optimizing.
6. we make "field is just identity" computable. then at the transform level
7. we replicate the transform's move semantics. that is, if it is the last use of a variable in the
   transform — do a move; if there will be a use after it — do a clone; and cache the index of the
   last use.
8. of course during optimization we replace all names with registers and do not even work with
   names at runtime.

# Passing parameters into evaluate and optimizing parameter passing

How do we pass and resolve parameters?
1. we make an interface to look up a parameter index by name and implement it in the read spec — to
   get the index from the source array.
2. then we make such an interface on the row that lets you get an element.
3. we also need to expose the list of fields required for the script, so that at the transform
   level we can do a correct move for getting an element.
